# Автоматичний довідник та історичний імпорт

Увімкнений чат і дозволений відправник перевіряються перед створенням будь-яких даних. Новий об’єкт береться з префікса перед двокрапкою після часу. Коди `РЧВ 7` і `РЧВ7` означають один об’єкт. Невідомий алгоритм створюється для цього об’єкта в категорії «Без категорії»; категорію можна змінити в адмінпанелі.

У назві зберігаються пороги, номери обладнання та змістовні дужки. Секції `(Зафіксовано…)`, `(Було: … Стало: …)`, `(День туру: …)` і `Тривалість:` не входять у назву. Переноси рядків та «на протязі»/«протягом» нормалізуються. Зелене повідомлення з іншими зафіксованими значеннями знаходить той самий алгоритм. Наявні ручні regex-правила та пріоритети зберігаються. Вимкнені об’єкти й правила не створюються повторно; повідомлення потрапляє на перевірку.

Кожен новий тип, створений автоматично або вручну, отримує чотири власні відповіді:

- Показники перевірено.
- Повідомлено відповідального.
- Виконано коригування.
- Втручання не знадобилося.

Це тестові тексти для редагування, а не автоматично надані відповіді. Вони мають окремі записи та версії для кожного алгоритму. Права на нові об’єкти й маршрути повідомлень налаштовує адміністратор у наявних довідниках.

## Імпорт вересня 2026

Виробничі повідомлення не включаються в публічний репозиторій чи артефакт збірки. Локальна копія знаходиться в ігнорованій директорії `.local-data`. GitHub secret `HISTORY_IMPORT_GZIP_BASE64` містить UTF-8 JSON, стиснений gzip та закодований base64. Workflow передає його в налаштування Azure `HistoryImport__GzipBase64`, не друкуючи значення. Якщо параметр відсутній, імпорт не запускається.

Під час старту після міграцій дані імпортуються однією SQL-транзакцією. Маркер `import:telegram-history:2026-09:v1` у `vpfalgo.Settings` фіксується разом із даними. Повторний деплой пропускає завершений імпорт, не змінюючи історію, назви, шаблони чи їх версії. Видаляти маркер або змінювати набір даних під цим самим маркером не слід.

Набір містить 104 повідомлення, 14 об’єктів, 36 типів алгоритмів та 57 випадків: 52 із завершенням, 5 без повідомлення про завершення. Для 5 із 52 завершених випадків початок обчислено як час завершення мінус тривалість із тексту. Решта початків береться з червоних повідомлень. Дата — з дати повідомлення, час — із тексту, часова зона — Київ.

Telegram ID вихідних чатів у надісланих фрагментах немає. Дані належать двом вимкненим джерелам «Архів: алгоритми РЧВ (вересень 2026)» і «Архів: алгоритми ВФС та НС (вересень 2026)». Це архівні записи, а не підключення до реальних чатів. Вони не породжують повідомлень чи нагадувань. Подальше зелене повідомлення з реального чату не закриває випадок в окремому архівному джерелі.

Неповні випадки не отримують вигаданого завершення. Mini App показує попередження про непідтверджений поточний стан. У Power BI доступне поле `Quality`:

| Значення | Значення для звіту |
|---|---|
| `historical` | Початок і завершення присутні |
| `historical_inferred_start` | Початок відновлений із тривалості |
| `historical_missing_end` | Немає повідомлення про завершення |
| `historical_duration_mismatch` | Час початку/завершення відрізняється від вказаної тривалості більш ніж на хвилину |

Всі імпортовані випадки залишаються «Без відповіді», доки працівник не надасть відповідь. Для звіту про поточні активні проблеми можна виключити `historical_missing_end`, а для середньої тривалості окремо враховувати відновлені початки.

## Перевірка

`pnpm --dir src/VPFAlgorithmBot/ClientApp test` перевіряє успішні порожні HTTP-відповіді й помилки API. `dotnet run --project tests/VPFAlgorithmBot.Tests/VPFAlgorithmBot.Tests.csproj -c Release` перевіряє розпізнавання, шаблони, доступ та імпорт. Без приватного параметра використовуються синтетичні дані; з `HistoryImport__GzipBase64` перевіряється повний наданий набір. Значення даних у тестовий лог не виводяться.

SQL-транзакції виконуються цілком усередині EF execution strategy. Транзакційний `sp_getapplock` запобігає дублюванню довідника й одночасному створенню одного випадку різними інстансами. Схема бази не змінюється.
