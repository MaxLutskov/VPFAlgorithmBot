# План розробки VPF Algorithm Bot

Версія 2.0 від 28 вересня 2026 року. Один повний тестовий випуск, потім комплексне тестування та виправлення. Архітектурний зразок: локальний `StockPartsBot` у сусідній папці.

## Функціональна модель

1. У підключеному Telegram-чаті з’являється повідомлення 🔴. Система створює спрацювання, визначає чат, об’єкт, категорію, алгоритм і час початку.
2. Відповідальні отримують приватне повідомлення від нового бота. **У Telegram-чаті з ботом** показуються кнопки із заготовленими відповідями й можливість написати власну відповідь. Кнопки «Взяти в роботу» немає.
3. Повідомлення 🟢 завершує спрацювання. Після завершення ті самі дії відповіді в чаті бота залишаються доступними.
4. Стан проблеми `Active/Resolved` і стан відповіді `Unanswered/Answered` незалежні. «Без відповіді» діє до першої відповіді; завершення проблеми його не скасовує.
5. **Telegram Mini App** містить адмінпанель, дешборд активних випадків і історію. Відповіді в Mini App не потрібні для основного робочого сценарію; їх надають у чаті бота.
6. Після відповіді зберігаються службове ім’я автора, текст, фактичний час і версія шаблону. Час завершення проблеми не змінюється. Не робити автоматичного висновку «Вирішено без втручання».

## Обов’язковий стек та розгортання

- ASP.NET Core на **.NET 10** і hosted services, як у StockPartsBot.
- **EF Core 10 + SQL Server provider**, цільова СУБД **Azure SQL Database**.
- Власна SQL-схема `vpfalgo` і власна таблиця `vpfalgo.__EFMigrationsHistory`. Схеми `stockparts` і `dbo` не змінювати.
- Telegram Bot API через `HttpClient`: локальний polling або тестовий імітатор; на Azure — webhook. Режими взаємовиключні.
- Mini App на React + TypeScript + Vite; збірка у `wwwroot/miniapp` ASP.NET Core застосунку. Авторизація через перевірку Telegram Mini App `initData` на сервері.
- Azure App Service Linux з .NET 10, `Always On`, `/health`, HTTPS; окремий застосунок із власним ботом, за сумісності на наявному App Service Plan.
- Azure Key Vault для адміністративного пароля через managed identity; локально .NET User Secrets. Адміністративна сесія прив’язана до особистого Telegram ID.
- GitHub Actions з OpenID Connect за підходом StockPartsBot. Реальний деплой проводиться після локального тестування й отримання доступів.
- SQL views у схемі `vpfalgo` та окрема роль читання для Power BI.

Версії пакетів узгодити з локальним StockPartsBot. Не переносити його секрети, connection string, Telegram-токен або ідентифікатори Azure-ресурсів. Повторно використовувати тільки перевірені архітектурні рішення й доречні компоненти коду.

## Повний обсяг тестового випуску

- декілька чатів, дозволені відправники, додавання й вимкнення джерел через Mini App;
- довідники ВФС, РЧВ1, РЧВ2, НС, ПНС, теплопунктів та нових об’єктів;
- категорії, типи алгоритмів і редаговані правила розпізнавання;
- зіставлення червоних і зелених повідомлень, захист від дублів і черга випадків для перевірки;
- призначення відповідальних за чатом, об’єктом і категорією, резервний адресат і нагадування;
- запит доступу через `/start`, підтвердження адміністратором, білий список, службові імена, ролі та scopes;
- приватні повідомлення відповідальним, вибір підготовленої відповіді прямо в чаті бота, власний текст;
- редактор шаблонів у Mini App з обов’язковою прив’язкою до конкретного алгоритму, версії та копія тексту на момент відповіді;
- у Mini App: активні випадки, усі випадки без відповіді, історія, картка, часові фільтри «сьогодні», «вчора», «за датами» і «за весь час» за датою початку в часі Києва, адміністративні налаштування та аудит;
- SQL views, словник даних і приклади запитів для Power BI;
- demo-режим, тести, інструкція запуску та тестовий звіт.

Не входять: запис дій назад у Zabbix, імпорт усієї минулої історії Telegram, готовий PBIX і зміни робочої Azure SQL. Підготовка звітних даних входить повністю.

## Послідовність однієї ітерації

1. **Основа:** solution, ASP.NET Core проєкт, EF Core контекст у `vpfalgo`, міграції, health endpoint, demo seed і налаштування. Збірка не потребує реальних секретів.
2. **Події:** Telegram webhook/polling та demo ingestion проходять через спільну логіку. Оригінал повідомлення зберігається до розпізнавання. Джерело перевіряється за chat ID та sender ID.
3. **Розпізнавання:** дата Telegram-повідомлення в Europe/Kyiv, час із тексту, окремий час отримання; об’єкт, категорія й алгоритм за налаштовуваними правилами. Спільний event ID має пріоритет у зіставленні; без нього використовуються стабільні ознаки. Неоднозначні випадки переходять на перевірку.
4. **Доступ:** запит у боті, схвалення в Mini App, службове ім’я, ролі та доступи до об’єктів. Права на кожну дію перевіряються сервером. Telegram `initData` перевіряється криптографічно.
5. **Маршрутизація:** кілька адресатів, пріоритет конкретного правила, резервний адресат. Подія та завдання надсилання зберігаються однією транзакцією. Повторні спроби й помилки видно адміністратору.
6. **Відповіді в чаті:** кнопки шаблонів і власний текст; підтримка активних і завершених випадків, зокрема старих повідомлень із кнопками. Кожна відповідь має автора й час; наступна не перезаписує першу.
7. **Mini App:** адміністративні CRUD для джерел, користувачів, довідників, правил, маршрутизації, шаблонів і нагадувань; робочий дешборд, історія, фільтри й аудит.
8. **Звітність та експлуатація:** SQL views «один рядок на спрацювання» й «один рядок на відповідь», словник полів, інструкція запуску, Azure-конфігурація та перевірка резервного відновлення.

## Дані та Power BI

Окремі таблиці `Users`, `UserScopes`, `Chats`, `AllowedSenders`, `Objects`, `Categories`, `AlgorithmTypes`, `ParserRules`, `RoutingRules`, `ResponseTemplates`, `ResponseTemplateVersions`, `IncomingMessages`, `Incidents`, `Responses`, `NotificationOutbox`, `NotificationAttempts`, `AuditEvents`, `Settings` у схемі `vpfalgo`.

Час у БД — UTC, у Mini App та повідомленнях — Europe/Kyiv. `AnswerState` визначається наявністю відповідей; історичний стан на задану дату відтворюється за часовими мітками. Налаштування та шаблони переживають міграції й оновлення.

Показники: початки й завершення за день; кількість за об’єктом/категорією/типом; тривалість `EndedAt - StartedAt`; час до першої відповіді `FirstResponseAt - StartedAt`; кількість завершених без відповіді на момент оновлення. Порожній час відповіді — `NULL`, а кілька відповідей не множать кількість спрацювань.

## Тестування після повної збірки

Провести domain-тести, інтеграційні тести API з тестовим SQL Server, браузерні тести Mini App та demo наскрізний прогін. Якщо тестової Azure SQL або SQL Server немає, ці перевірки позначити `BLOCKED`, а не підміняти SQLite. Реальний Bot_Outlook, Key Vault і App Service перевірити окремо після надання доступів.

Критичні сценарії: 🔴 → активний без відповіді; 🟢 → завершений без відповіді; відповідь у чаті після 🟢 → завершений з відповіддю без зміни `EndedAt`; повтор update і callback; кілька одночасних відповідей; повторне спрацювання того самого алгоритму; однаковий текст у різних чатах; неоднозначне зелене; опівніч; блокування користувача; версії шаблонів; недоступність Telegram; перезапуск; міграція; правильність SQL views.

Контрольний приклад: початок 07:02:57, завершення 09:07:57, відповідь 09:20:00 тієї самої дати. Тривалість проблеми 2 год 5 хв; час до відповіді 2 год 17 хв 3 с; відповідь через 12 хв 3 с після завершення.

Скласти `docs/TEST_REPORT.md` з `PASS/FAIL/BLOCKED`, доказами й режимом перевірки. Виправити P0/P1, повторити зачеплені тести та фінальний наскрізний прогін.

Після реалізації проведи повний набір тестів, виправ помилки й повтори наскрізний сценарій. Без зовнішніх секретів доведи demo-режим, а реальні інтеграції познач як неперевірені. Не змінюй робочу базу й не виконуй деплой до підготовки конфігурації.
